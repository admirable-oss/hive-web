# How to Run Parallel AI Coding Agents With tmux and Git Worktrees

If you want to run parallel AI coding agents without adding an agent manager to your stack, Git and tmux are a useful foundation. Git gives each task its own working directory and branch. tmux gives each process a terminal window you can revisit after disconnecting from that terminal.

The pattern is simple: one independent task, one worktree, one tmux window, one agent. The details matter, though. Dependencies, local services, credentials, shell quoting, and review still need deliberate handling. This walkthrough builds a small launcher for Claude Code and shows where the pattern needs human judgment.

## What you need

- A Git repository with a committed starting point.
- tmux installed and available on your `PATH` (`brew install tmux` on macOS with Homebrew, or your Linux distribution’s package manager).
- Claude Code installed and authenticated for the launcher below. Other terminal coding agents can be started manually in the same worktrees.
- A Unix-like shell with Bash.

Before you begin, commit or stash changes in your main checkout. New worktrees start from a commit; uncommitted edits in the original directory are not copied into them. Keep credentials out of prompts and task notes, and use your usual secure development setup for environment variables.

## Why combine Git worktrees and tmux?

A Git worktree is another checkout associated with the same repository. Each one has a separate directory, `HEAD`, and index, while sharing the repository’s objects and most history. That makes it practical to keep several branches checked out side by side. The [Git worktree manual](https://git-scm.com/docs/git-worktree) covers the commands and their behavior.

tmux is a terminal multiplexer. Its server holds sessions and windows independently of the terminal client, so you can detach and reconnect while the host remains up. This helps when an SSH connection drops; it does not keep a process alive through a reboot or machine failure. See the [tmux manual](https://man7.org/linux/man-pages/man1/tmux.1.html) for session and client commands.

Neither tool is an access-control boundary. A worktree separates files on disk, but an agent process still runs with the permissions of its user. Use operating-system or agent-level sandboxing for access restrictions.

## 1. Create one worktree for each task

From the repository root, create branches from the current commit:

```sh
git worktree add -b agent/auth ../myapp-auth
git worktree add -b agent/search ../myapp-search
git worktree list
```

Give each agent a task that can be reviewed independently. “Add the password reset endpoint and its tests” is a better work assignment than “work on authentication.” If two tasks need to change the same interface, agree on that contract first or do the work in sequence.

Git will not normally check out the same local branch into multiple worktrees. Keep one branch per task and avoid forcing the same branch into two directories. Worktrees reduce accidental edits to the same checkout; they do not guarantee that separate branches will merge without conflicts.

## 2. Prepare each worktree

Tracked files appear in a new worktree. Ignored or untracked local state generally does not. Depending on the project, the agent may need dependencies installed, test databases started, generated files created, or a distinct development-server port.

For a JavaScript project, change into each worktree and use the package manager and lockfile the repository expects. Keep installs consistent with its documented workflow. For local servers, assign explicit ports such as `3101` and `3102` if the application supports configuration that way.

Do not blindly copy `.env` files into every agent workspace. They can contain production credentials or broad access tokens. Prefer a development-only credential source with the minimum access needed, and give an agent secrets only when its task requires them. Likewise, do not assume that a worktree provides isolation from files elsewhere on the machine.

## 3. Start sessions manually once

Before automating, try the workflow by hand. Start a tmux session, then create a window for each task:

```sh
tmux new-session -s agents
```

In the first window, run:

```sh
cd ../myapp-auth
claude "Read the repository instructions. Implement only the auth task; inspect first, run relevant checks, and report the changed files and results. Do not commit or merge."
```

Create another window with `Ctrl-b c`, move between windows with `Ctrl-b n` and `Ctrl-b p`, and start the next agent from its worktree. Detach with `Ctrl-b d`; reattach later with:

```sh
tmux attach-session -t agents
```

This manual pass helps catch missing setup before a script creates a larger batch. It also makes the relationship between each tmux window and its Git branch easy to understand.

## 4. Use a small launcher for repeated setup

Once the manual loop works, save the following as `parallel-agents.sh` in the repository root. It validates task names, creates a branch and worktree for each task, and starts a Claude Code session in its own tmux window. It intentionally does not copy environment files, install arbitrary dependencies, auto-commit, or merge branches.

```bash
#!/usr/bin/env bash
set -eu

if [ "$#" -eq 0 ]; then
  printf 'Usage: %s task-name [task-name ...]\n' "$0" >&2
  exit 2
fi

command -v git >/dev/null 2>&1 || { echo "git is required" >&2; exit 1; }
command -v tmux >/dev/null 2>&1 || { echo "tmux is required" >&2; exit 1; }
command -v claude >/dev/null 2>&1 || { echo "Claude Code (claude) is required" >&2; exit 1; }

repo=$(git rev-parse --show-toplevel)
repo_parent=$(dirname "$repo")
repo_name=$(basename "$repo")
session="agents-$repo_name"
seen=""

for task in "$@"; do
  case "$task" in
    ''|*[!a-zA-Z0-9_-]*) echo "Task names may contain only letters, numbers, _ and -: $task" >&2; exit 2 ;;
  esac
  case " $seen " in
    *" $task "*) echo "Duplicate task name: $task" >&2; exit 2 ;;
  esac
  seen="$seen $task"
done

if [ -n "$(git -C "$repo" status --porcelain)" ]; then
  echo "Commit or stash changes in the main worktree before launching agents." >&2
  exit 1
fi

if tmux has-session -t "$session" 2>/dev/null; then
  echo "tmux session already exists: $session" >&2
  exit 1
fi

for task in "$@"; do
  branch="agent/$task"
  worktree="$repo_parent/$repo_name-$task"
  if [ -e "$worktree" ]; then
    echo "Worktree path already exists: $worktree" >&2
    exit 1
  fi
  if git -C "$repo" show-ref --verify --quiet "refs/heads/$branch"; then
    echo "Branch already exists: $branch" >&2
    exit 1
  fi
done

for task in "$@"; do
  branch="agent/$task"
  worktree="$repo_parent/$repo_name-$task"
  git -C "$repo" worktree add -b "$branch" "$worktree"
done

tmux new-session -d -s "$session" -n control -c "$repo"
for task in "$@"; do
  worktree="$repo_parent/$repo_name-$task"
  prompt="Read repository instructions first. Implement only the $task task. Inspect before editing, run relevant checks, and report changed files and results. Do not commit or merge."
  printf -v quoted_prompt '%q' "$prompt"
  tmux new-window -d -t "$session" -n "$task" -c "$worktree" "claude $quoted_prompt"
done

if [ -n "${TMUX:-}" ]; then
  tmux switch-client -t "$session"
else
  tmux attach-session -t "$session"
fi
```

Make it executable and start two independent tasks:

```sh
chmod +x parallel-agents.sh
./parallel-agents.sh auth search
```

Each window begins with a task-specific prompt. Claude Code’s CLI accepts an initial prompt as a positional argument; consult the [CLI reference](https://docs.anthropic.com/en/docs/claude-code/cli-usage) if its invocation changes. The script deliberately uses `printf %q` before passing the prompt through tmux’s shell command. It also limits task names to a safe character set rather than inserting arbitrary input into a shell command.

This is a starter, not a general-purpose process supervisor. If creating a later worktree fails, remove any earlier worktrees it created before retrying. If a coding agent exits, inspect that window and decide whether to relaunch it. For other agent CLIs, adapt the one command in `tmux new-window` to that tool’s documented syntax rather than assuming every CLI accepts the same prompt format.

## 5. Review and merge one task at a time

The script leaves the agent changes uncommitted so you can inspect them first. From the main checkout, check each worktree’s state and diff:

```sh
git -C ../myapp-auth status --short
git -C ../myapp-auth diff
git -C ../myapp-search status --short
git -C ../myapp-search diff
```

Run the relevant checks inside each worktree. Then stage and commit the changes you accept on their task branches. Merge one branch at a time from the target branch, resolving design conflicts before continuing. Review generated files and dependency-lock changes carefully; two otherwise separate tasks can still make incompatible updates there.

Keep the human review gate. An agent can explain its changes, but its own summary is not a substitute for reading the diff and checking the result. If a task has expanded beyond its original scope, narrow or split it before asking another agent to build on top of it.

## 6. Clean up after integration

After a branch has been integrated and its worktree is clean, remove the linked checkout and delete the branch if you no longer need it:

```sh
git worktree remove ../myapp-auth
git branch -d agent/auth
git worktree list
```

If Git refuses to remove a worktree because it contains changes, stop and inspect them first. Do not use `--force` as routine cleanup; it can discard work you have not reviewed. `git worktree prune` is for stale administrative entries after a worktree directory has already gone missing, not a replacement for removing active worktrees.

## When to keep the DIY workflow

tmux and worktrees are a good fit when you want direct control, use a terminal comfortably, and have a small number of independent tasks. The setup makes each agent’s directory and branch visible, and it is easy to adapt to another terminal agent.

An agent manager may help when you need a shared task board, a persistent view of many sessions, or a coordinated review queue. Compare those tools on their isolation model, permission handling, supported agents, and how easily you can recover work outside the tool. For the broader planning and integration method, read [our guide to managing multiple AI coding agents](/blog/manage-multiple-ai-coding-agents/).

Hive solves a neighboring runtime problem: keeping coding-agent sessions available across local and remote machines. A persistent session is useful when a terminal disconnects, but it does not replace the task isolation and review process in this tutorial. ## A compact checklist

- Start from a known commit; commit or stash changes in the main checkout.
- Create one branch and worktree per independent task.
- Prepare dependencies, local services, and ports deliberately.
- Keep credentials out of copied worktree files and prompts.
- Use one tmux window per worktree, and remember detach is not machine-level persistence.
- Inspect diffs and run checks before committing or merging.
- Integrate branches one at a time, then clean up only reviewed work.

The useful outcome is not three agents running at once. It is three pieces of work that remain understandable, reviewable, and safe to integrate. Start with two small tasks, learn where your workflow slows down, and add more concurrency only when the review loop can keep up.
